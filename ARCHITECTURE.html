Retail Intelligence & Autonomous Store Decision Platform

Single-file guide to the project: what it does, how it's built, how the agents decide, how data moves end to end, and how to run it locally. Databricks (Bronze → Silver → Gold) feeds a LangChain-driven Supervisor plus six deterministic specialists and a new IntelligentRetailAgent that emits Pydantic-validated structured output, selects tools dynamically, and falls back safely on failure. Every output passes NeMo-style guardrails; a quantitative optimization engine, baseline-vs-AI simulation, and a golden-dataset evaluation harness score decision quality; the C# API (via a FastAPI agents service) serves the React dashboard; and consequential actions are gated by role-based HITL governance with an append-only audit trail.

Author: Pradeep Sahoo  ·  Purpose: Learning implementation. Not a certified production system.

1The business problem

Every retail store runs on a stream of time-pressured decisions that happen before the doors open. They are small individually, large in aggregate, and today they are made from gut and spreadsheets rather than from the data every POS and WMS already generates.

The daily questions

  • What goes on the front display today?
  • Which SKUs need to move between stores before they stock out or age out?
  • Which prices should slide down this week before margin bleeds further?
  • What's a realistic 7-day revenue target to steer the team toward?
  • Which aging items need a bundle vs. an outright markdown?

What goes wrong today

  • Fast movers understocked while slow movers age in back-rooms.
  • Blanket markdowns that erode margin unnecessarily.
  • Stale product mix on prime front-office real estate.
  • Inconsistent decisions across stores — no shared playbook.
  • Pricing and discount actions that are not reliably auditable.

Why it isn't a data problem

POS, inventory, returns, and surveys already generate the signals. The gap is that nobody has time to synthesize five signals × fifty SKUs × five stores every morning — and when they do, no one can later prove why a markdown was approved.

What this platform is: a decision assistant for that morning window — a prioritized daily action plan per store, grounded in evidence, bounded by guardrails, and gated by human approval.

2The architecture selected

A layered, lakehouse-first, agentic AI platform with a fail-closed safety layer and an explicit human gate. Seven layers, each owning one responsibility and talking to the next through an explicit contract.

The nine layers

  • Source systems — POS · inventory · returns · surveys · trends
  • Databricks Lakehouse — Bronze → Silver → Gold
  • Tool boundary — ToolRegistry (typed, read-only)
  • Security guard — ACLs · PII mask · prompt-injection scan around every tool call
  • Agentic AI — LangChain Supervisor + 6 specialists + IntelligentRetailAgent + quantitative optimizer
  • Guardrails — NeMo or local policy engine (fail-closed, audited)
  • Decision augmentation — Explainability · Simulation · Evaluation
  • Agents service (FastAPI) → ASP.NET Core Web API — Clean Architecture
  • Experience & HITL governance — React UI, HTML report, RBAC approvals with TTL + idempotency

Four cross-cutting invariants

  • Agents never touch the data store directly — only via ToolRegistry.
  • No write path from the LLM — only C# executes, after a human approves.
  • Append-only audit log — every decision reconstructible.
  • LLM shapes narrative + selects tools; the deterministic specialists own every number.

Why this shape

  • Separation by decision domain — each specialist is testable and swappable.
  • Structured LLM output (Pydantic) with deterministic fallback — reproducible, auditable, runs offline.
  • Typed read-only tool boundary + ACL/PII/injection guard — smallest possible blast radius for LLM mistakes.
  • C#-mediated write path — the service enforces invariants and owns the audit trail.
  • Evaluation + simulation attached to every bundle — the system can measure its own decisions, not just produce them.
  • Closed feedback loop — realized KPIs feed back into Bronze on the next ingest.

3The engineering trade-offs

Every design decision bought something and cost something. The important ones, with what we gained, what we gave up, and the signal that would make us revisit the call.

1 · Deterministic specialists over LLM-only agents

Gained

Reproducibility · unit-testable scoring · auditable metrics · no API key or cost dependency.

Gave up

Flexible reasoning · open-ended planning · zero-shot generalization to novel scenarios.

Signal to revisit

Scoring rules become too brittle to maintain and a judgment-call layer would clearly earn its keep.

2 · Supervisor + six specialists over one monolithic agent

Gained

Bounded contexts · per-domain accountability · specialists evolve independently.

Gave up

Orchestration code to maintain · cross-domain reasoning harder to express in one place.

Signal to revisit

A specialist that keeps bleeding into another's territory — repeatedly needing data or verdicts from a sibling.

3 · Typed, read-only ToolRegistry over direct data access

Gained

A boundary we can audit · the LLM cannot run SQL or shell commands · every data read is traceable.

Gave up

A tool surface to maintain and version · a new data need always forces a new tool.

Signal to revisit

Tool count explodes to the point maintenance eats the benefit — likely never, since the ceiling is bounded by domain actions.

4 · Local policy engine fallback over NeMo-only guardrails

Gained

Stack runs anywhere without GPU/CUDA · identical fail-closed contract · tests don't need NeMo installed.

Gave up

A duplicate policy implementation to keep in sync between the two engines.

Signal to revisit

Policy drift between the two engines — a case where NeMo blocks and the local engine lets through, or vice versa.

5 · In-memory recommendation repo over SQL from day one

Gained

Zero-setup iteration speed · fast test runs · clean swap boundary for later persistence.

Gave up

Persistence between runs · multi-process sharing of recommendations.

Signal to revisit

Approval workflow outlives a single process — plug in the already-designed EF Core + Postgres repository.

6 · Dual data adapters (Databricks SQL + local CSV) behind one facade

Gained

Offline runs · deterministic fixtures · cheap tests · no cloud account required to demo.

Gave up

Two implementations to keep in sync behind one RetailDataStore contract.

Signal to revisit

Edge-case drift — if CSV passes something SQL rejects, the facade contract is too loose.

7 · Human approval on every consequential action

Gained

No runaway automation · legally defensible decisions · trust from store teams.

Gave up

Speed · the dream of fully autonomous stores · 24/7 execution without an on-call human.

Signal to revisit

Not negotiable for pricing, transfers, markdowns, replenishment — this gate is a core property, not a shortcut.

8 · Append-only audit log over mutable records

Gained

Perfect reconstruction of any past decision · immutable evidence trail for compliance.

Gave up

Storage grows monotonically over time.

Signal to revisit

Not the design — the retention policy. Cold-tier archival of audit older than N quarters is the mitigation.

9 · Standalone HTML report alongside the React UI

Gained

A shareable, printable, offline artifact for stakeholders without UI access.

Gave up

Duplicate rendering effort for the same underlying data model.

Signal to revisit

The two drift in what they show — a divergence would mean the report has become its own second source of truth.

10 · LangChain over a hand-rolled tool-calling loop

Gained

Battle-tested retry · streaming · provider swapping · parsing-error recovery — all with one dependency instead of ~80 lines of code we'd have to maintain.

Gave up

A heavy top-level dependency and exposure to LangChain's API churn across versions.

Signal to revisit

LangChain breaks on a major version in a way we can't absorb — swap to the thin ReAct loop we already had.

11 · Pydantic-validated structured output (AgentPlan) over free-form LLM text

Gained

Deterministic parsing · one repair loop · drop-safe fallback · no downstream has to parse ambiguity.

Gave up

The LLM is slightly less expressive; one failed-and-repaired call costs ~2× LLM tokens.

Signal to revisit

Repair-rate climbs over ~5% — tighten the schema or switch model.

12 · Retry/timeout/fallback at the tool layer (not just the LLM)

Gained

Most agent failures come from flaky tools; a CallRecord trace rides on every bundle so ops can see which tool is the problem without full distributed tracing.

Gave up

~10% overhead from telemetry; opt-out via RetryPolicy(max_attempts=1).

Signal to revisit

When OpenTelemetry is wired to a real backend, strip the local trace and lean on spans.

13 · FastAPI agents service as the one HTTP contract between .NET and Python

Gained

Connection pooling · observability hooks · single serialization boundary · the agent system is testable in isolation.

Gave up

One more process to run (one more Dockerfile, one more port). ~30 MB RAM overhead.

Signal to revisit

Latency floor becomes a problem — move to a shared in-process host or gRPC.

14 · Golden-dataset evaluation over LLM-as-judge

Gained

Frozen regression tripwire; precision/recall/F1 move with the code; catches drift at CI time.

Gave up

Humans must curate and maintain the dataset — it won't scale to every edge case.

Signal to revisit

Dataset coverage drops below ~70% of production patterns — layer in offline log replay.

15 · SIMULATED label + open assumptions dictionary on every impact number

Gained

Every "+8% revenue" claim ships with the coefficient that produced it — the assumptions are impossible to hide in a demo.

Gave up

Numbers look less bold next to a disclaimer; marketing may push back.

Signal to revisit

Only once we have validated A/B outcomes to replace the heuristics — then the disclaimer narrows, not disappears.

16 · Governance in-memory for the learning scope, pluggable for production

Gained

Clean interface · fast tests · zero infra · state machine + audit log + idempotency work today.

Gave up

No persistence across process restarts; cannot share state between replicas yet.

Signal to revisit

Governance outlives one process — back it with Postgres + outbox behind the existing interface.

17 · Observability facade over hard OpenTelemetry dependency

Gained

Agent code emits spans unconditionally; real OTel exports when enabled, in-memory sink in CI.

Gave up

The facade is one more abstraction; a reader has to look up LocalTracer before the real exporter.

Signal to revisit

If OTel becomes a hard prerequisite in deployment, drop the local sink.

18 · Security as test suite, not just docs

Gained

ACL · PII mask · injection scan · tool authz enforced by code with 12 regression tests — a security-design.md can lie, a test suite can't.

Gave up

Patterns drift from real production attack lists; must be refreshed.

Signal to revisit

Red-team finds a bypass — add the pattern and the regression in the same PR.

4Project overview

For every store, the platform generates a prioritized daily action plan: front-office product placements, inter-store transfers, replenishment, aging-inventory interventions, pricing optimization, and a 7-day sales target. Every recommendation carries evidence, risk, expected revenue and margin impact, required approval, confidence, and a success KPI.

What it produces

A RecommendationBundle: insights, prioritized action plan, full agent trace, and per-action evidence. Printable as a standalone HTML daily report.

Who runs it

A store manager (approves and executes), a regional lead (sees KPIs and pricing), and operations (audits approvals).

Why agents?

Each specialist owns one concern (pricing, inventory, forecast, etc.). The Supervisor orchestrates and validates. Deterministic by default — no LLM API key required to run end-to-end.

RBAC state machine (pending → approved → executed) · TTL expiry · idempotency keys · auto-escalation on margin / transfer thresholds · append-only audit entries per transition.

Observability

OpenTelemetry-compatible tracer + metrics sink with a local fallback for CI. Counters, histograms, span records for every tool call, LLM round-trip, and recommendation outcome.

Experience

React 18 + TypeScript + Vite · Recharts · 7-page dashboard · printable HTML report. Every recommendation ships with an explainability block (evidence refs with timestamps, scoring breakdown, confidence rationale).

GitHub Actions: Python (3.11 & 3.12 matrix) · .NET 8 build/test · React build · docker-compose e2e smoke · soft-fail bandit + pip-audit security scans.

Local stack

Docker Compose: agents (FastAPI, port 7071) → api (.NET 8, port 5080) → ui (nginx + Vite build, port 5173). One docker compose up to run everything.

6Each layer explained

What each layer is responsible for, which parts of the repository implement it, and the one invariant it enforces for the layer above.

Layer 1 Source systems POS · WMS · CRM · external feeds
What it is

The operational truth — point-of-sale baskets, inventory snapshots, returns and survey events, plus external signals like weather and search demand. Everything downstream has to come from here, directly or by derivation.

Repository parts
  • External in production; locally simulated by databricks/generate_sample_data.py (50 products × 5 stores × 90 days, deterministic).
Invariant for the next layer

Every record carries a timestamp and a store/product id; nothing is emitted without them.

Layer 2 Databricks Lakehouse Delta · Bronze → Silver → Gold
What it is

Delta Lake medallion. Bronze lands raw events append-only; Silver de-duplicates, casts types, and conforms keys; Gold aggregates the feature tables the agents actually consume.

Serving tables (Gold)
  • agg_product_sales_features
  • agg_inventory_features
  • agg_store_performance_90d
  • product_trend
Repository parts
  • databricks/ — SQL DDL + Bronze/Silver/Gold notebooks
  • ai-agents/retail_agents/data_access.py — RetailDataStore facade with Databricks SQL and local CSV adapters behind the same contract
Invariant for the next layer

Agents never see raw rows — only typed, trusted features. The facade switch is invisible to agent code.

Layer 3 Tool boundary ToolRegistry — typed, read-only
What it is

The single door through which agents access data. Each tool is a plain Python function with JSON-serializable inputs and outputs, registered in a typed catalog. Every call is auditable back to a recommendation.

Representative tools
  • get_sales(store_id, …)
  • get_inventory_position(store_id)
  • get_nearby_stores(store_id, max_distance_km)
  • get_trend(product_id)
Repository parts
  • ai-agents/retail_agents/tools.py
Invariant for the next layer

No write path exists. No tool mutates state. The LLM cannot run SQL or shell commands. Guardrails enforce the allow-list on every call.

Layer 4 Agentic AI Supervisor + 6 specialists
What it is

A deterministic, auditable orchestration. The Supervisor plans the run, invokes RetailIntelligenceAgent first for context, then dispatches the five scoring/decision specialists, dedupes conflicts, and finally hands the ranked list to StoreExecutionAgent to turn into a plan.

Specialists
  • RetailIntelligence — store context + insights pack.
  • ProductRecommendation — composite retail score for front-office placement.
  • InventoryOptimization — three concerns: transfers, aging, replenishment.
  • PricingOptimization — elastic markdowns bounded by a hard margin floor.
  • SalesForecasting — 7-day target with day-of-week seasonality.
  • StoreExecution — prioritizes by (priority, −expected_margin_impact).
Repository parts
  • ai-agents/retail_agents/supervisor.py
  • ai-agents/retail_agents/agents/*.py
  • ai-agents/retail_agents/llm_provider.py — pluggable; deterministic default means no API key needed.
Invariant for the next layer

Every recommendation carries evidence, scores, approval flag, and a success KPI. The LLM shapes narrative only — it never alters metrics.

Layer 5 AI Guardrails NeMo or local policy engine · fail-closed
What it is

Three policy stages — Input, Tool, Output — plus an append-only Audit Log. Each stage denies by default. If NVIDIA NeMo Guardrails is installed, it runs the policies; otherwise the local engine enforces the same contract.

Policies
  • Input: validation · prompt-injection detection · PII mask · topic restriction.
  • Tool: allow-list · schema check · read-only enforcement.
  • Output: evidence present · grounded to known IDs · approval tag correct for the action type.
  • Audit: approvals, rejections, violations — immutable.
Repository parts
  • ai-guardrails/ — NeMo config + service/guardrail_service.py local engine.
  • ai-guardrails/tests/ — security tests.
Invariant for the next layer

Anything the API receives has already been policy-validated and grounded. Hallucinated IDs cannot reach the service layer.

Layer 6 ASP.NET Core Web API Clean Architecture · .NET 8
What it is

Four-project Clean Architecture solution. The Infrastructure project orchestrates the Python agent process and the guardrail client. The Application project holds use-cases and validators. The Domain project holds the invariants. The Api project is the HTTP surface.

Projects
  • Retail.Domain — entities, value objects, invariants.
  • Retail.Application — services, DTOs, FluentValidation.
  • Retail.Infrastructure — agent orchestrator, guardrail client, in-memory recommendation repo.
  • Retail.Api — controllers, Program, Swagger, Serilog, problem-details middleware.
Repository parts
  • api/Retail.sln and the four project folders.
Invariant for the next layer

Only the API writes to downstream systems, and only after an approval record exists for the recommendation.

What it is

Seven-page dashboard plus a printable standalone HTML report. Managers see KPIs, the daily game plan, and the agent trace; consequential actions (pricing, transfers, markdowns, replenishment) require explicit approval, which is written to the append-only audit log alongside the agent's evidence snapshot.

UI pages

7The intelligent agent — structured output + resilience

IntelligentRetailAgent is the upgraded agentic loop. It asks the LLM to emit a Pydantic-validated AgentPlan JSON, validates it against business rules, runs the planned tools under retry + timeout + telemetry, and hands off to the deterministic specialists for the authoritative numbers. On any failure, it falls back to a hard-coded safe plan — the system never stalls on an LLM outage.

Structured output contract

# ai-agents/retail_agents/intelligent_agent.py
class AgentPlan(BaseModel):
    intent: str
    store_id: str
    tool_calls: list[ToolCall] = Field(
        default_factory=list, max_length=12)
    expected_outputs: list[str] = []
    confidence: float = Field(..., ge=0.0, le=1.0)
    fallback_strategy: str = "deterministic_specialists"

Resilience primitives

  • RetryPolicy — attempts, delay, timeout, backoff.
  • with_retry() — threading-based timeout (works on Windows), exponential backoff, per-attempt CallRecord.
  • Repair loop — one shot at coaxing the LLM to re-emit valid JSON before falling back.
  • Call trace rides on every output bundle for post-hoc debugging.

Dynamic tool selection

  • LLM selects which of the 9 registered tools to call based on the user intent.
  • Plan is validated: unknown intents / tools / low confidence trigger fallback.
  • Capped at max_iterations=6, tool_calls max_length=12 — runaway loops are impossible.

8Quantitative inventory optimization

Moves the system from "recommend an action" to "optimize a decision" with textbook inventory-theory formulas. All deterministic, all stdlib-only, all auditable.

Core formulas

safety_stock = z(service_level) · σ_daily · √L
reorder_point = μ_daily · L + safety_stock
EOQ = √(2 · D_annual · K / (c · h))
P(stockout) = ½ · erfc((on_hand − μ·L) / (σ·√L · √2))

Blended demand forecast

Exponential smoothing (α=0.3) blended 60/40 with the historical mean — reduces lag versus pure smoothing while keeping explainability. Day-of-week seasonality covered by the seven_day_forecast baseline for 7-day targets.

Store-level allocation

Proportional fair-share across stores by expected demand. Floor-and-remainder step guarantees Σ allocated == available (no rounding drift). Supplier MOQ/MaxOQ clamping via apply_supplier_constraints().

Composite retail score — ProductRecommendationAgent

Each candidate product is scored across five normalized factors; the weighted sum ranks front-office placement candidates. Weights are configurable, deliberately avoiding over-reliance on any single signal.

score = 0.30·velocity + 0.25·margin + 0.20·demand + 0.15·sentiment + 0.10·availability
  • Velocity0.30
  • Margin0.25
  • Demand0.20
  • Sentiment0.15
  • Availability0.10

Decision rules — other specialists

  • Transfer: source cover ≥ 12 wk & destination near reorder → move excess, keep 8 wk at source.
  • Aging: age ≥ 180d → prefer bundle/promo; markdown ≤ 15% only when margin cushion allows.
  • Replenishment: weekly velocity > on-hand → flag with lead-time & vendor.
  • Pricing: projected margin must stay above the 10% floor; else reject.
  • Forecast: 7-day target = seasonal baseline × stretch factor (default +5%).
  • Execution: sort by priority then -expected_margin_impact.

12Explainability — the five questions each recommendation answers

Every recommendation ships with an explainability block answering: why, what evidence supports it, what's the expected impact, what's the confidence, and what could go wrong. A store manager can read, challenge, or override it with full context.

Evidence references

Each referenced metric lists its source (e.g. sales_90d), metric (e.g. weekly_velocity), value, and recorded_at timestamp. A reviewer can replay any decision against the data as it existed when the agent ran.

Scoring breakdown

For FRONT_OFFICE actions, each of the five weighted components (velocity · margin · demand · sentiment · availability) is listed with its weight and raw value. The composite score is never a black box.

Confidence rationale

Narrative sentence derived from the numeric confidence plus the count of named risks: "high confidence — multiple strong signals align; 2 named risks tracked". No bare numbers without context.

Role-based permissions

  • Store Manager — FRONT_OFFICE, REPLENISH.
  • Regional Manager — TRANSFER, MARKDOWN, AGING_REVIEW, FRONT_OFFICE (override).
  • Finance Approver — PRICING, MARKDOWN.
  • Auditor — read-only.

Auto-escalation thresholds

  • |Expected margin impact| ≥ $500 → Regional.
  • Price change ≥ 10% → Finance.
  • Transfer units ≥ 100 → Regional.
  • Any MARKDOWN or PRICING → Finance / Regional.

Idempotency + TTL

  • Key = SHA-256 of {rec_id, store, product, action, day}.
  • Intake twice with same key = same governed record.
  • Execute twice = no-op (replayable safely).
  • Pending for > 24 h → auto-expired.

14Business impact simulation — baseline vs AI

SIMULATED — not actual outcomes. Compares a do-nothing week against the week the AI-recommended plan is executed, using an open dictionary of planning heuristics so every claim is auditable. The disclaimer and the assumptions dict ride on every output.

Metrics compared

  • Revenue + revenue Δ%
  • Gross profit + margin pp Δ
  • Units sold / stockouts / aged units remaining
  • Carrying cost (annual rate × leftover units / 52)
  • Net profit Δ, sell-through improvement %

Why open assumptions matter

Executive dashboards often hide the coefficients behind a dramatic percentage. Here every coefficient is listed with the output. A reviewer can swap any value and re-run; the disclaimer tells them the result is directional, not predictive.

15Evaluation harness — can we trust the agent?

A regression tripwire for recommendation quality. Hand-labelled golden scenarios + forecast ground-truth + business-constraint checks + a false-positive detector. Runs in CI so drift is caught at PR time.

Golden scenarios

Hand-curated test cases: given this input state, this is what the agent SHOULD recommend (expected_action_types) and SHOULD NOT (forbidden_action_types). Precision / recall / F1 computed over hits and forbidden emissions.

Forecast error

  • WAPE — robust to zeros, bounded [0, ∞).
  • MAPE — unstable near zero, kept for parity with legacy BI.
  • Bias — mean (forecast − actual) / actual; positive = over-forecasting.

False positive detector

  • Markdown on a fast mover (velocity ≥ 15/wk).
  • Feature a chronic returner (return rate > 20%).
  • Transfer from a low-cover source (< 2 weeks).
  • Price change on zero stock.

16Observability — tracer + metrics facade

OpenTelemetry-compatible façade that exports to the configured OTLP endpoint when enabled and the SDK is installed, and falls back to an in-memory MetricsSink suitable for CI assertions otherwise. Every signal the agent system cares about is captured.

Spans

tracer.span("supervisor.analyze", attrs) around every agent step. The in-memory sink records name, duration, status, and attributes so tests can assert on them.

Counters & histograms

  • tool_invocations_total{name,status}
  • tool_duration_ms{name} (histogram)
  • llm_tokens_total{model,kind}
  • recommendation_outcomes_total{action,state}

17Security & data governance

Security as code, not documentation. Every tool call is wrapped by guarded_call(): principal / ACL / tool authz check → prompt-injection scan → invoke → PII mask on the result. Audit log records every allow and deny.

Row-level ACLs

Principal(user_id, role, allowed_stores, allowed_tools). Access to a store_id outside the principal's allow-list is refused and audited. Tool-level authz works the same way.

PII masking

  • email · phone · ssn · card · customer_id
  • Recursive on dicts and lists — the LLM never sees cleartext PII.
  • Non-strings pass through unchanged.

Prompt-injection patterns

  • "ignore previous instructions" family
  • "act as admin / developer / root"
  • "reveal your system prompt"
  • Chat-template tokens (<|im_start|> etc.)
  • "print the API key / secret / token"

Secrets handling

SecretsManager reads from env vars, requires non-empty values, and the mask_for_log() helper masks anything with an API_KEY / SECRET / TOKEN / PASSWORD suffix before it reaches logs.

Tool authorization

Every call runs through authorize_tool_call(principal, name, args) — bundling ACL + tool allow-list + injection scan. Returned PII is masked before leaving the call boundary.

Audit log

Every allow/deny decision writes {timestamp, actor, role, action, resource, decision, reason}. Separate from the governance audit log; both are append-only.

18Trust & safety boundaries

Agents can't touch data directly

All data access flows through ToolRegistry — typed, read-only, allow-listed.

No write path from the LLM

Tools are strictly read. All execution is C#-mediated and only after a human approval record exists.

Fail-closed guardrails

Input, tool, and output policies deny by default. Violations logged with full context.

Grounding on known IDs

Every recommendation must reference real store_id / product_id seen in Gold.

Append-only audit

Approvals, rejections, violations, and executed actions are immutable and reconstructible.

Deterministic by default

No LLM API key? The deterministic specialists still produce the full plan — the LLM only shapes narrative.

20CI / CD pipeline

Four GitHub Actions workflows under .github/workflows/ — path-filtered so a UI-only PR doesn't spin up the Python matrix, and vice versa.

python.yml

  • Matrix: Python 3.11 & 3.12.
  • Runs the 45 data-free unit tests (optimization, evaluation, governance, security, simulation + explainability).
  • Legacy data-dependent tests run only when sample CSVs are present.
  • Soft-fail ruff lint, bandit SAST, pip-audit dep scan.

dotnet.yml

  • .NET 8 restore / build / test on the full solution.
  • CI relaxes TreatWarningsAsErrors (strict locally).
  • Uploads TRX test results as an artifact.

ui.yml

  • Node 20; npm install (no lockfile committed yet).
  • Soft-fail lint / type-check / build / test / npm audit.

e2e-stack.yml

  • Manual dispatch — brings up docker compose all three services.
  • Health-polls GET /health on the .NET API before smoke call.
  • Dumps compose logs on failure; tears down on cleanup.

Security scanning

  • Bandit — Python static analysis.
  • pip-audit — Python dependency CVEs.
  • npm audit --audit-level=high for the UI.

Caching

  • pip cache keyed on ai-agents/requirements.txt.
  • Default Node cache for subsequent runs.
  • Docker buildx GHA cache for compose builds (manual run).

21Quick start & operate

Run the whole stack locally. The Python half runs with no cloud account; the C# API and React UI need .NET 8 and Node 20. The agents service is containerized alongside them.

1. One-command full stack (recommended)

docker compose up --build
# agents (FastAPI, port 7071) → api (.NET 8, port 5080) → ui (nginx+Vite, port 5173)
# Each service has a healthcheck; `ui` waits for `api`, `api` waits for `agents`.

2. Generate deterministic sample data

python databricks/generate_sample_data.py
# 50 products × 5 stores × 90 days → 17,369 sales / 250 inventory snapshots / 1,024 surveys

3. End-to-end agent run (no API, no UI)

# Deterministic stdlib supervisor
PYTHONPATH=ai-agents python -m retail_agents.supervisor S101

# LangChain-driven supervisor (narrative + tool-calling)
PYTHONPATH=ai-agents python -m retail_agents.langchain_supervisor S101

# Full intelligent agent (structured output + resilience)
PYTHONPATH=ai-agents python -m retail_agents.intelligent_agent S101

4. Call the FastAPI agents service directly

pip install -r ai-agents/requirements.txt
pip install fastapi uvicorn
PYTHONPATH=ai-agents python ai-agents/service.py
# POST /recommendations/S101
# POST /recommendations/S101/intelligent
# POST /recommendations/S101/langchain
# POST /simulation/S101        — baseline vs AI
# POST /evaluation             — golden-dataset + WAPE/MAPE
# GET  /metrics                — observability snapshot

5. LLM backend (optional)

export RETAIL_LC_PROVIDER=anthropic    # or openai, or none for offline fake
export RETAIL_LC_MODEL=claude-opus-4-7
export ANTHROPIC_API_KEY=sk-ant-...

6. Produce the standalone HTML decision report

python reports/generate_report.py S101
# → reports/daily-store-decision-report.html (styled, 38 action cards)

7. Run the test suite

PYTHONPATH=ai-agents python -m pytest
# 71 tests — 45 new (optimization, evaluation, governance, security,
#   simulation, explainability) + 26 legacy (agents, guardrails, sample data).

8. Manual pieces (if not using docker-compose)

# API
cd api && dotnet run --project Retail.Api --urls http://localhost:5080

# UI (in a second shell)
cd ui && npm install && npm run dev
# → open http://localhost:5173
