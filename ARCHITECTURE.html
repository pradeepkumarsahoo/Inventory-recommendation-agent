Composite retail score — ProductRecommendationAgent

Each candidate product is scored across five normalized factors; the weighted sum ranks front-office placement candidates. Weights are configurable, deliberately avoiding over-reliance on any one signal.

score = 0.30·velocity + 0.25·margin + 0.20·demand + 0.15·sentiment + 0.10·availability
  • Velocity0.30
  • Margin0.25
  • Demand0.20
  • Sentiment0.15
  • Availability0.10

Decision rules — other specialists

  • Transfer: source cover ≥ 12 wk & destination near reorder → move excess, keep 8 wk at source.
  • Aging: age ≥ 180d → prefer bundle/promo; markdown ≤ 15% only when margin cushion allows.
  • Replenishment: weekly velocity > on-hand → flag with lead-time & vendor.
  • Pricing: projected margin must stay above the 10% floor; else reject.
  • Forecast: 7-day target = seasonal baseline × stretch factor (default +5%).
  • Execution: sort by priority then -expected_margin_impact.

3End-to-end flow — what happens on one run

A single call to python -m retail_agents.supervisor S101 — or one POST /api/stores/{id}/recommendations — exercises the whole stack. Each step below declares its input and output contract.

Ingest to Bronze

POS, inventory, returns, surveys, and external feeds land in bronze.* Delta tables with ingest timestamps. No business logic at this layer — just typed capture.

In: source systems Out: bronze.*

Conform to Silver

De-duplicate, cast types, resolve late-arriving data, apply reference joins (store, product dim). Data quality expectations attach here as delta constraints.

In: bronze.* Out: silver.*

Aggregate to Gold features

Build serving tables for agents: agg_product_sales_features, agg_inventory_features, agg_store_performance_90d, product_trend.

Switch: Databricks SQL / local CSV via RetailDataStore

Supervisor plans the run

Receives a store id. Runs the input guardrail. Loads the insights pack via RetailIntelligenceAgent. Decides which specialists to call and in what order — intelligence first, execution last.

Policy: fail-closed on any input violation

Specialists emit candidates

Each specialist produces evidence-bearing candidates: composite score, expected revenue + margin impact, risk, confidence, success KPI, and whether human approval is required. All data reads flow through ToolRegistry.

Determinism: no LLM API key needed to run end-to-end

Guardrails validate every output

Each candidate passes the output policy: evidence present, grounded to real store/product IDs, approval flag correct for the action type. Rejections are recorded in the agent trace with reason — never silently dropped.

Audit: append-only; verdict + reason + evidence hash

Dedupe & rank

Supervisor collapses conflicts (e.g. one pricing action per product, keeping the one with the greater margin impact), then ranks by priority and expected margin impact.

Out: deduped recommendation list

Build the action plan

StoreExecutionAgent turns ranked recommendations into numbered actions with owners, deadlines (deadline_hours), and success KPIs — the manager's single pane of work for the day.

Sort: (priority, -expected_margin_impact)

API serves the bundle

The .NET Infrastructure project orchestrates the Python agent run, validates the DTO with FluentValidation, logs via Serilog, and surfaces errors as RFC 7807 problem-details through a controller.

Entity: RecommendationBundle

UI and report present the plan

React pages render KPIs, agent trace, and recommendation cards. The standalone HTML report mirrors the UI for print/offline review.

Components: KpiTile · RecommendationCard · StoreSelector

Human approves consequential actions

Pricing, transfers, markdowns, and replenishment require explicit manager approval. Both approvals and rejections are written to the append-only audit log with user, timestamp, reason, and the evidence snapshot the agent used.

HITL gate: no consequential write without an approval record

Audited execution & feedback

Only the C# service executes — never the LLM or the agents. Adapters push approved actions to ERP, pricing engine, or WMS; every call is tied back to the recommendation id. Realized outcomes flow into Bronze on the next ingest, closing the loop plan → act → measure.

Invariant: no write path from LLM

5Trust & safety boundaries

Agents can't touch data directly

All data access flows through ToolRegistry — typed, read-only, allow-listed by the guardrail layer.

No write path from the LLM

Tools are strictly read. All execution is C#-mediated and only after a human approval record exists.

Fail-closed guardrails

Input, tool, and output policies deny by default. Any violation is logged with full context.

Grounding on known IDs

Every recommendation must reference real store_id / product_id seen in Gold; hallucinated IDs are rejected.

Append-only audit

Approvals, rejections, policy violations, and executed actions are immutable and reconstructible.

Deterministic by default

No LLM API key? The deterministic specialists still produce the full action plan — the LLM only shapes narrative.
