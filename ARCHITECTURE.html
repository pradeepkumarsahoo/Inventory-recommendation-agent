Retail Intelligence & Autonomous Store Decision Platform

Single-file guide to the project: what it does, how it's built, how the agents decide, how data moves end to end, and how to run it locally. Databricks (Bronze → Silver → Gold) feeds a Python Supervisor + six specialist agents; every output passes NeMo-style guardrails; the C# API serves the React dashboard; and consequential actions are gated by human approval with an append-only audit trail.

Author: Pradeep Sahoo  ·  Purpose: Learning implementation. Not a certified production system.

1The business problem

Every retail store runs on a stream of time-pressured decisions that happen before the doors open. They are small individually, large in aggregate, and today they are made from gut and spreadsheets rather than from the data every POS and WMS already generates.

The daily questions

  • What goes on the front display today?
  • Which SKUs need to move between stores before they stock out or age out?
  • Which prices should slide down this week before margin bleeds further?
  • What's a realistic 7-day revenue target to steer the team toward?
  • Which aging items need a bundle vs. an outright markdown?

What goes wrong today

  • Fast movers understocked while slow movers age in back-rooms.
  • Blanket markdowns that erode margin unnecessarily.
  • Stale product mix on prime front-office real estate.
  • Inconsistent decisions across stores — no shared playbook.
  • Pricing and discount actions that are not reliably auditable.

Why it isn't a data problem

POS, inventory, returns, and surveys already generate the signals. The gap is that nobody has time to synthesize five signals × fifty SKUs × five stores every morning — and when they do, no one can later prove why a markdown was approved.

What this platform is: a decision assistant for that morning window — a prioritized daily action plan per store, grounded in evidence, bounded by guardrails, and gated by human approval.

2The architecture selected

A layered, lakehouse-first, agentic AI platform with a fail-closed safety layer and an explicit human gate. Seven layers, each owning one responsibility and talking to the next through an explicit contract.

The seven layers

  • Source systems — POS · inventory · returns · surveys · trends
  • Databricks Lakehouse — Bronze → Silver → Gold
  • Tool boundary — ToolRegistry (typed, read-only)
  • Agentic AI — Supervisor + 6 specialists (deterministic by default)
  • Guardrails — NeMo or local policy engine (fail-closed, audited)
  • ASP.NET Core Web API — Clean Architecture
  • Experience & HITL — React UI, HTML report, human approvals

Three cross-cutting invariants

  • Agents never touch the data store directly — only via ToolRegistry.
  • No write path from the LLM — only C# executes, after a human approves.
  • Append-only audit log — every decision reconstructible.

Why this shape

  • Separation by decision domain — each specialist is testable and swappable.
  • Deterministic scoring with the LLM as narrative-only — reproducible, auditable, runs with no API key.
  • Typed read-only tool boundary — smallest possible blast radius for LLM mistakes.
  • C#-mediated write path — the service enforces invariants and owns the audit trail.
  • Closed feedback loop — realized KPIs feed back into Bronze, so next day's recommendations are measurable against yesterday's commitments.

3The engineering trade-offs

Every design decision bought something and cost something. The important ones, with what we gained, what we gave up, and the signal that would make us revisit the call.

1 · Deterministic specialists over LLM-only agents

Gained

Reproducibility · unit-testable scoring · auditable metrics · no API key or cost dependency.

Gave up

Flexible reasoning · open-ended planning · zero-shot generalization to novel scenarios.

Signal to revisit

Scoring rules become too brittle to maintain and a judgment-call layer would clearly earn its keep.

2 · Supervisor + six specialists over one monolithic agent

Gained

Bounded contexts · per-domain accountability · specialists evolve independently.

Gave up

Orchestration code to maintain · cross-domain reasoning harder to express in one place.

Signal to revisit

A specialist that keeps bleeding into another's territory — repeatedly needing data or verdicts from a sibling.

3 · Typed, read-only ToolRegistry over direct data access

Gained

A boundary we can audit · the LLM cannot run SQL or shell commands · every data read is traceable.

Gave up

A tool surface to maintain and version · a new data need always forces a new tool.

Signal to revisit

Tool count explodes to the point maintenance eats the benefit — likely never, since the ceiling is bounded by domain actions.

4 · Local policy engine fallback over NeMo-only guardrails

Gained

Stack runs anywhere without GPU/CUDA · identical fail-closed contract · tests don't need NeMo installed.

Gave up

A duplicate policy implementation to keep in sync between the two engines.

Signal to revisit

Policy drift between the two engines — a case where NeMo blocks and the local engine lets through, or vice versa.

5 · In-memory recommendation repo over SQL from day one

Gained

Zero-setup iteration speed · fast test runs · clean swap boundary for later persistence.

Gave up

Persistence between runs · multi-process sharing of recommendations.

Signal to revisit

Approval workflow outlives a single process — plug in the already-designed EF Core + Postgres repository.

6 · Dual data adapters (Databricks SQL + local CSV) behind one facade

Gained

Offline runs · deterministic fixtures · cheap tests · no cloud account required to demo.

Gave up

Two implementations to keep in sync behind one RetailDataStore contract.

Signal to revisit

Edge-case drift — if CSV passes something SQL rejects, the facade contract is too loose.

7 · Human approval on every consequential action

Gained

No runaway automation · legally defensible decisions · trust from store teams.

Gave up

Speed · the dream of fully autonomous stores · 24/7 execution without an on-call human.

Signal to revisit

Not negotiable for pricing, transfers, markdowns, replenishment — this gate is a core property, not a shortcut.

8 · Append-only audit log over mutable records

Gained

Perfect reconstruction of any past decision · immutable evidence trail for compliance.

Gave up

Storage grows monotonically over time.

Signal to revisit

Not the design — the retention policy. Cold-tier archival of audit older than N quarters is the mitigation.

9 · Standalone HTML report alongside the React UI

Gained

A shareable, printable, offline artifact for stakeholders without UI access.

Gave up

Duplicate rendering effort for the same underlying data model.

Signal to revisit

The two drift in what they show — a divergence would mean the report has become its own second source of truth.

4Project overview

For every store, the platform generates a prioritized daily action plan: front-office product placements, inter-store transfers, replenishment, aging-inventory interventions, pricing optimization, and a 7-day sales target. Every recommendation carries evidence, risk, expected revenue and margin impact, required approval, confidence, and a success KPI.

What it produces

A RecommendationBundle: insights, prioritized action plan, full agent trace, and per-action evidence. Printable as a standalone HTML daily report.

Who runs it

A store manager (approves and executes), a regional lead (sees KPIs and pricing), and operations (audits approvals).

Why agents?

Each specialist owns one concern (pricing, inventory, forecast, etc.). The Supervisor orchestrates and validates. Deterministic by default — no LLM API key required to run end-to-end.

6Each layer explained

What each layer is responsible for, which parts of the repository implement it, and the one invariant it enforces for the layer above.

Layer 1 Source systems POS · WMS · CRM · external feeds
What it is

The operational truth — point-of-sale baskets, inventory snapshots, returns and survey events, plus external signals like weather and search demand. Everything downstream has to come from here, directly or by derivation.

Repository parts
  • External in production; locally simulated by databricks/generate_sample_data.py (50 products × 5 stores × 90 days, deterministic).
Invariant for the next layer

Every record carries a timestamp and a store/product id; nothing is emitted without them.

Layer 2 Databricks Lakehouse Delta · Bronze → Silver → Gold
What it is

Delta Lake medallion. Bronze lands raw events append-only; Silver de-duplicates, casts types, and conforms keys; Gold aggregates the feature tables the agents actually consume.

Serving tables (Gold)
  • agg_product_sales_features
  • agg_inventory_features
  • agg_store_performance_90d
  • product_trend
Repository parts
  • databricks/ — SQL DDL + Bronze/Silver/Gold notebooks
  • ai-agents/retail_agents/data_access.py — RetailDataStore facade with Databricks SQL and local CSV adapters behind the same contract
Invariant for the next layer

Agents never see raw rows — only typed, trusted features. The facade switch is invisible to agent code.

Layer 3 Tool boundary ToolRegistry — typed, read-only
What it is

The single door through which agents access data. Each tool is a plain Python function with JSON-serializable inputs and outputs, registered in a typed catalog. Every call is auditable back to a recommendation.

Representative tools
  • get_sales(store_id, …)
  • get_inventory_position(store_id)
  • get_nearby_stores(store_id, max_distance_km)
  • get_trend(product_id)
Repository parts
  • ai-agents/retail_agents/tools.py
Invariant for the next layer

No write path exists. No tool mutates state. The LLM cannot run SQL or shell commands. Guardrails enforce the allow-list on every call.

Layer 4 Agentic AI Supervisor + 6 specialists
What it is

A deterministic, auditable orchestration. The Supervisor plans the run, invokes RetailIntelligenceAgent first for context, then dispatches the five scoring/decision specialists, dedupes conflicts, and finally hands the ranked list to StoreExecutionAgent to turn into a plan.

Specialists
  • RetailIntelligence — store context + insights pack.
  • ProductRecommendation — composite retail score for front-office placement.
  • InventoryOptimization — three concerns: transfers, aging, replenishment.
  • PricingOptimization — elastic markdowns bounded by a hard margin floor.
  • SalesForecasting — 7-day target with day-of-week seasonality.
  • StoreExecution — prioritizes by (priority, −expected_margin_impact).
Repository parts
  • ai-agents/retail_agents/supervisor.py
  • ai-agents/retail_agents/agents/*.py
  • ai-agents/retail_agents/llm_provider.py — pluggable; deterministic default means no API key needed.
Invariant for the next layer

Every recommendation carries evidence, scores, approval flag, and a success KPI. The LLM shapes narrative only — it never alters metrics.

Layer 5 AI Guardrails NeMo or local policy engine · fail-closed
What it is

Three policy stages — Input, Tool, Output — plus an append-only Audit Log. Each stage denies by default. If NVIDIA NeMo Guardrails is installed, it runs the policies; otherwise the local engine enforces the same contract.

Policies
  • Input: validation · prompt-injection detection · PII mask · topic restriction.
  • Tool: allow-list · schema check · read-only enforcement.
  • Output: evidence present · grounded to known IDs · approval tag correct for the action type.
  • Audit: approvals, rejections, violations — immutable.
Repository parts
  • ai-guardrails/ — NeMo config + service/guardrail_service.py local engine.
  • ai-guardrails/tests/ — security tests.
Invariant for the next layer

Anything the API receives has already been policy-validated and grounded. Hallucinated IDs cannot reach the service layer.

Layer 6 ASP.NET Core Web API Clean Architecture · .NET 8
What it is

Four-project Clean Architecture solution. The Infrastructure project orchestrates the Python agent process and the guardrail client. The Application project holds use-cases and validators. The Domain project holds the invariants. The Api project is the HTTP surface.

Projects
  • Retail.Domain — entities, value objects, invariants.
  • Retail.Application — services, DTOs, FluentValidation.
  • Retail.Infrastructure — agent orchestrator, guardrail client, in-memory recommendation repo.
  • Retail.Api — controllers, Program, Swagger, Serilog, problem-details middleware.
Repository parts
  • api/Retail.sln and the four project folders.
Invariant for the next layer

Only the API writes to downstream systems, and only after an approval record exists for the recommendation.

Layer 7 Experience & HITL React 18 · TypeScript · Vite + HTML report
What it is

Seven-page dashboard plus a printable standalone HTML report. Managers see KPIs, the daily game plan, and the agent trace; consequential actions (pricing, transfers, markdowns, replenishment) require explicit approval, which is written to the append-only audit log alongside the agent's evidence snapshot.

UI pages
  • Executive dashboard, Product intelligence, Inventory optimization, Pricing, Agent decision center, Daily game plan, Architecture.
Reusable components
  • KpiTile · RecommendationCard · StoreSelector
Repository parts
  • ui/ — React source; API client at ui/src/services/api.ts.
  • reports/generate_report.py → reports/daily-store-decision-report.html.
Invariant upheld

No consequential write happens without a logged human approval.

Composite retail score — ProductRecommendationAgent

Each candidate product is scored across five normalized factors; the weighted sum ranks front-office placement candidates. Weights are configurable, deliberately avoiding over-reliance on any single signal.

score = 0.30·velocity + 0.25·margin + 0.20·demand + 0.15·sentiment + 0.10·availability
  • Velocity0.30
  • Margin0.25
  • Demand0.20
  • Sentiment0.15
  • Availability0.10

Decision rules — other specialists

  • Transfer: source cover ≥ 12 wk & destination near reorder → move excess, keep 8 wk at source.
  • Aging: age ≥ 180d → prefer bundle/promo; markdown ≤ 15% only when margin cushion allows.
  • Replenishment: weekly velocity > on-hand → flag with lead-time & vendor.
  • Pricing: projected margin must stay above the 10% floor; else reject.
  • Forecast: 7-day target = seasonal baseline × stretch factor (default +5%).
  • Execution: sort by priority then -expected_margin_impact.

8End-to-end flow — what happens on one run

A single call to python -m retail_agents.supervisor S101 — or one POST /api/stores/{id}/recommendations — exercises the whole stack. Each step below declares its input and output contract.

Ingest to Bronze

POS, inventory, returns, surveys, and external feeds land in bronze.* Delta tables with ingest timestamps.

In: source systems Out: bronze.*

Conform to Silver

De-duplicate, cast types, resolve late-arriving data, apply reference joins.

In: bronze.* Out: silver.*

Aggregate to Gold features

Build serving tables for agents.

Switch: Databricks SQL / local CSV via RetailDataStore

Supervisor plans the run

Receives a store id. Runs the input guardrail. Loads the insights pack via RetailIntelligenceAgent. Decides which specialists to call.

Policy: fail-closed on any input violation

Specialists emit candidates

Each specialist produces evidence-bearing candidates with score, expected revenue + margin impact, risk, confidence, success KPI, and approval flag.

Determinism: no LLM key needed to run end-to-end

Guardrails validate every output

Each candidate passes the output policy: evidence present, grounded to real IDs, approval flag correct.

Audit: append-only; verdict + reason + evidence hash

Dedupe & rank

Collapses conflicts (one pricing action per product, keeping the greater margin impact), ranks by priority and margin impact.

Out: deduped recommendation list

Build the action plan

StoreExecutionAgent turns ranked recommendations into numbered actions with owners, deadlines, and success KPIs.

Sort: (priority, -expected_margin_impact)

API serves the bundle

Infrastructure orchestrates the Python run, validates the DTO, logs via Serilog, surfaces errors as RFC 7807 problem-details.

Entity: RecommendationBundle

UI and report present the plan

React pages render KPIs, agent trace, and recommendation cards; the standalone HTML report mirrors it for print/offline.

Components: KpiTile · RecommendationCard · StoreSelector

Human approves consequential actions

Pricing, transfers, markdowns, and replenishment require explicit manager approval, written to the append-only audit log.

HITL gate: no consequential write without an approval record

Audited execution & feedback

Only the C# service executes. Adapters push approved actions to downstream systems. Realized outcomes flow into Bronze on the next ingest.

Invariant: no write path from LLM

10Trust & safety boundaries

Agents can't touch data directly

All data access flows through ToolRegistry — typed, read-only, allow-listed.

No write path from the LLM

Tools are strictly read. All execution is C#-mediated and only after a human approval record exists.

Fail-closed guardrails

Input, tool, and output policies deny by default. Violations logged with full context.

Grounding on known IDs

Every recommendation must reference real store_id / product_id seen in Gold.

Append-only audit

Approvals, rejections, violations, and executed actions are immutable and reconstructible.

Deterministic by default

No LLM API key? The deterministic specialists still produce the full plan — the LLM only shapes narrative.

12Quick start & operate

Run the whole stack locally. The Python half runs with no cloud account; the C# API and React UI need .NET 8 and Node 20.

1. Generate deterministic sample data

python databricks/generate_sample_data.py
# 50 products × 5 stores × 90 days → 17,369 sales / 250 inventory snapshots / 1,024 surveys

2. Produce the standalone HTML decision report

python reports/generate_report.py S101
# → reports/daily-store-decision-report.html (styled, 38 action cards)

3. End-to-end agent run (no API, no UI)

PYTHONPATH=ai-agents python -m retail_agents.supervisor S101
# Returns a RecommendationBundle JSON — agent trace, action plan, 38 recommendations.

4. Run the test suite

python -m pytest
# 26/26 passing — agents, guardrails, sample data.

5. Boot the full stack

# API
cd api && dotnet run --project Retail.Api --urls http://localhost:5080

# UI (in a second shell)
cd ui && npm install && npm run dev
# → open http://localhost:5173
